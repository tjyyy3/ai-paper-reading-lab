# 方法笔记：为什么这样切、这样问、这样核

这篇分享的做法不是"把论文丢给模型然后相信它"，而是把"AI 读论文"拆成三个可以分别检查的环节：**切分（锚点）→ 提问（输出契约）→ 核查（机械校验 + 人工判定）**。下面解释每一步的设计理由和取舍，也包括这套方法在哪里失效。

---

## 1. 阅读难点到底出在哪一环

拿这篇论文举例。一句在社交媒体上流传的转述是"长上下文模型会忽略中间的信息"。要判断这句话能不能用在自己的场景里，读者实际需要三样东西：

1. **结论的量级**：忽略到什么程度？（原文：GPT-3.5-Turbo 可下降 >20%，最差时低于不给文档的 56.1%）
2. **结论的适用条件**：在什么任务、多少文档、哪些模型、什么指标下测的？
3. **结论的反面证据**：有没有模型/设置不服从这个规律？

这三样东西在原文里的物理位置是**分散**的：

| 需要的信息 | 原文位置 | 锚点 | 页码 |
| --- | --- | --- | --- |
| 结论与量级 | §2.3 正文 + Table 1 | S23P2 / T1 | p.5 |
| 任务定义（恰好一篇含答案） | §2.1 第 1 段 | S21P1 | p.3 |
| 数据与文档粒度 | §2.1 第 2 段 | S21P2 | p.3 |
| 指标与解码 | §2.1 第 4 段、§2.2 | S21P3 / S22P1 | p.3–4 |
| 模型清单与版本 | §2.2（含脚注 5、6） | S22P1 / S22P2 | p.4–5 |
| 反例（Claude KV 近满分、LongChat 趋势不同） | §3.2 第 1–2 段、Fig. 7 图注 | S32P1 / S32P2 / FIG7 | p.6–7 |
| 机制是假设不是结论 | §4.1 第 3 段 | S41P3 | p.7 |

（页码由 `tools/locate_anchors.py` 机械定位，见 `evidence/anchor_pages.md`。）

这就是难点：**结论在摘要，限定在正文，反例在另一节的第二段，假设写在 "We hypothesize" 那半句里。** 单遍摘要会把第 1 行写得很准，然后把第 2–7 行丢掉——不是因为它读错，而是因为"总结"这个指令本身只要求第 1 行。

## 2. 为什么不用"整篇塞进去，让模型自己找"

- **成本与注意力**：这篇论文本身就在说，把更多内容塞进上下文不一定更好用。用 18 页全文去问一个 5 句话能答的问题，是在复制它批评的模式。
- **无法定位**：整篇输入下模型给的答案依然是一段自然语言，读者仍然不知道哪句话对应原文哪一段。**能不能定位，和答案对不对，是两件事。**
- **可复现性**：全文输入的结果依赖模型窗口、分块策略、随机性；固定一份 1200 词的节选，别人可以拿到一模一样的输入。

所以这里选择**人为控制输入**：把与阅读问题相关的段落摘出来，按论证单元切分，每段给一个锚点。代价是"我可能漏摘了某一段"——这个风险由"锚点↔原文位置对照表 + 页码反查"来暴露：如果某个锚点对不上 PDF，说明我摘错了或改写了。

## 3. 为什么按"段落"切，而不是按 token 窗口

- **段落是作者的论证单元**。一个限定条件往往正好是一段话（例如 §2.1 第 1 段的 "exactly one"）。
- **固定窗口会切断句子**，导致引文跨块：读者拿到的"逐字引文"一半在块 A、一半在块 B，校验器无法判断。按段落切 + 允许 `[...]` 省略，可以把"跨块"变成"块内省略"。
- **锚点必须可引用**。`S23P2` 这种名字比"第 37 个 chunk"更适合人读，也比页码稳定：论文从 v1 到 v3 页码会漂移，章节结构不会。

锚点命名规则：`S<章节><P段序>`（`S23P2` = §2.3 第 2 段），表格与图用 `T1`、`FIG5`，摘要用 `ABS`。

## 4. 为什么要求 (结论, 锚点, 逐字引文) 三元组

这是整套方法的核心取舍。如果只要求"给出处"，模型会写"见 §2.3"——这种引用无法核查，因为整节都可能相关。要求**逐字引文**，才能把核查降级成一个字符串包含判断：

```
canon(引文) ⊂ canon(所引锚点段落)
```

其中 `canon` 是"只保留小写字母和数字"的归一键。这样做的理由：

- 校验过程不需要模型参与，任何人跑脚本都能得到同样结果；
- 如果要求"改写后引用"，校验就退化成"这两句话意思是否一致"，而这个判断恰恰是我们要约束的对象。

代价也很直接：**逐字引文只证明"这句话在原文里"，不证明"这句话支持这个结论"**。这个盲区是实测出来的，见第 6 节。

## 5. 校验器怎么做，以及为什么这么笨

`verify/check_answers.py` 做三件事：

1. 从答案里解析 markdown 表格（含"锚点""逐字引文"列），按未转义的 `|` 切格（`\|` 视为内容）；
2. 把引文与锚点段落归一化后做子串判断，分三类：`ok` / `wrong_anchor`（引文在别的锚点里）/ `not_verbatim`（哪儿都没有）；
3. 检查"结论"里的数字是否出现在所引段落里。

为什么不做得更"智能"：

- 加语义相似度会让结果不可复现，也会把"模型对不对"变成"另一次模型判断对不对"；
- 归一化必须足够激进：PDF 抽取会把 `GPT-3.5` 抽成 `GPT-\n3.5`、把破折号抽成乱码，只有去掉标点、按词归一，两种版式才会落到同一个键上。这一步在 `tools/locate_anchors.py` 里有同一个实现的注释。

## 6. 实测暴露的三个盲区（不是设计时就想到的）

1. **真实但不相关的引文**。B 组有 4 行是"材料未给出"，却各配了一句真实原文（例如用 "We empirically study how language models use long input contexts..." 去支撑"query-aware contextualization 材料未给出"）。机械校验全部通过——因为引文确实在原文里。**格式强制会诱发"凑引文"。**
2. **多锚点行**。C 组有一行同时引 `S21P3` 和 `S22P1`（指标定义 + greedy 解码）。第一版校验器只认第一个锚点，会把正确的行判成"锚点错配"。已改为"任一被引锚点包含即通过"。
3. **正则扫描的假阴性**。我的覆盖度扫描器把 A 组的"20/30 篇文档"判成"未提到上下文规模"，因为正则写的是 `20 篇`（带空格），而原文写的是 `20/30 篇`。**机械扫描只能当提示，不能当结论。**

## 7. 对照组的取舍

- **A vs A2**：A 的提示词要求"300 字左右"。这既限制了覆盖度，也可能是它漏掉限定条件的原因之一。为避免把"字数上限"误当成"提示词风格"的效应，加了 A2：同样的一句话，只把字数限制改成"不限字数，可以写详细"。**如果 A2 仍然漏，说明漏的原因是"没有要求给证据"，不是"字数不够"。**
- **B vs C**：只差两件事——C 多了"先列条件清单"和"必须找反例"。这样差异可以归因到这两个动作。
- **不做多次重复**：n=1、每格一次。理由是本项目的目标是"演示一条可复现的阅读流程"，不是测量提示词效应量；重复 5 次×4 组会显著增加成本，而结果仍受单篇论文、单个模型限制。这一点在 README 的局限里明确声明，不当作稳定性结论。

## 8. 为什么不让模型自己核查自己的答案

自评会复用它自己的错误前提：模型倾向于认为"我引的当然支持我的结论"。所以核查被拆成两层：

- **机械层**（脚本）：只管"引文是否逐字存在于所引段落"，可复现、无解释空间；
- **人工层**（我）：判定"这条条件是否讲对、讲到什么程度"，写在 `verify/coverage_judgement.md`，每条都指到答案里的具体句子。

两层都留了原始输出，读者可以不同意我的判定并重新算。
